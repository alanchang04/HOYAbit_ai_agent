## 0. 全景：一次查詢會發生什麼

```
使用者問題（自由文字）
   │
   ▼ Stage 1  Query Understanding ────────── 1 次 LLM
   │  抽出 asset / horizon / research_goal
   │
   ▼ Stage 2  Feature Extraction ─────────── 8 個 factor 各自打真實 API（併發）
   │  每個 factor 有自己的抓取邏輯、自己的欄位、自己的時間尺度單位
   │
   ▼ Stage 3  Knowledge Layer ────────────── 純讀檔，刻意不打 LLM
   │  這個 factor「本身」的金融知識（適用尺度、關聯訊號、學術出處）
   │
   ▼ Stage 4  Dynamic Evidence Weight ────── Prior Weight（算）× Modifier（1 次 LLM）
   │  Prior 三種來源 → 換算到同一把尺；Modifier 讀四條線索給 [0.5, 2.0]
   │
   ▼ Stage 5  Evidence Card ＋ Prioritization  組裝層，不重新運算
   │  統一格式卡片，依 |evidence_weight| 排序
   │
   ▼ Stage 6  Evidence Graph ─────────────── 建圖，不重新判斷關係
   │  把 Stage 3 已寫好的 confirms/conflicts/independent 畫成邊
   │
   ▼ adapter  Evidence Card → Evidence 物件
   │
   ▼ Stage 7-9  既有推理鏈 run_reasoning() ── 最多 7 次 LLM
      Step A 事實層 → Step B 交叉驗證 → C1/C2 正反辯論（最多 2 輪）
      → Step D 裁判＋結論 → L5 三維信心分數
```

**LLM 呼叫總數**：1（Stage 1）+ 1（horizon 換算）+ 8（各 factor 的 Stage 4 modifier）
+ 最多 7（推理鏈）≈ **最多 17 次**。Stage 2 抓資料與 Stage 3 讀知識庫**完全不打 LLM**。

**一個貫穿全流程的原則**：算不出來的東西**整格不產生**，不留 `null`。
理由寫在 `stage_specs.py:483`——留 `null` 會被下游讀成「這次剛好沒算出來、下次可能有」，
整格不存在才傳達得出「這個 factor 結構性沒有這個東西」。未產生的格子會列在
`report.unresolved_fields` 裡，不是靜靜消失。

## 1. Stage 1 — Query Understanding

**端點**：`POST /api/stage1`（`stage1_demo_api.py:784`）

單一 LLM 呼叫，同時抽三個欄位（不是三次獨立呼叫）：

| 欄位 | 內容 |
|---|---|
| `asset` | 幣種代號陣列（BTC/ETH/SOL/BNB/XRP） |

## 2. Stage 2 — Feature Extraction（8 個 factor，全部真實 API）

`KNOWN_FACTORS`（`:204`）：

| factor | 型別 | 資料源 | window 單位 | 免 key |
|---|---|---|---|---|
| `funding_rate` | Statistical | Binance `fapi/v1/fundingRate` | 天（每 8h 一筆，日 3 筆） | ✅ |
| `active_address` | Statistical | blockchain.info Charts `n-unique-addresses` | 天 | ✅ |
| `momentum` | Statistical | 本地 CSV 算 RSI14（重用 `agent/collectors/price._rsi14`） | 天 | 本地 |
| `price` | Statistical | CoinGecko `simple/price`（退 CryptoCompare） | 天 | ✅ |
| `cpi` | **Event** | FRED `fredgraph.csv?id=CPIAUCSL` | **月**（不是天） | ✅ |
| `panews_sentiment` | **Sentiment** | PANews `universal-api.panewslab.com/articles` | 天（僅決定翻多深） | ✅ |
| `etf` | Event/資金流 | bitbo.io ETF flow 頁面（HTML 解析） | 天 | ✅ |
| `orderbook_depth` | **Snapshot** | Binance `fapi/v1/depth`（limit=1000） | **無 window** | ✅ |

### 2.1 四種型別的結構差異（不是同一套邏輯換名字）

這是 v3 最重要的設計主張之一——**四種型別的欄位集合本質不同**：

- **Statistical**：有完整的 `current_value` / `percentile` / `trend` / `slope` /
  `z_score`，可現場算 IC
- **Event**（cpi）：離散事件，**沒有「每天的值」**可以跟每天的 forward_return 配對
  → 結構性算不出 IC
- **Sentiment**（panews）：分數是**簡化版關鍵字計分**，不是 NLP 模型（`_panews_article_score`,
  `:1349`）。yaml 本身就記錄這是臨時代理，`nonzero_ratio` 就是這套方法的覆蓋率
- **Snapshot**（orderbook_depth）：**當下這一瞬間**的盤口。沒有母體可比，所以
  `percentile` / `trend` / `slope` **一律不產生**

### 2.2 window 的三種不同語意（容易誤解的地方）

- `funding_rate` / `active_address`：window = **回看幾天**，由 LLM 依 horizon 判斷
- `cpi`：window 單位是**月**——重用日頻判斷結果再換算，不另設一套月頻 prompt
- `panews_sentiment`：window **只決定往回翻多深，不是過濾邊界**。超出窗口的文章
  標記為非近期但**照樣計入**。翻不到底時 `window_covered=false` 並說明只翻到哪天
- `orderbook_depth`：**沒有 window 這個參數**

### 2.3 已知的資料源限制（誠實揭露，不是 bug）

- `active_address` **只支援 BTC**——blockchain.info 僅涵蓋 BTC UTXO 鏈，查其他幣
  直接回錯誤說明原因（`:990`）
- blockchain.info 位址計數有「當日未收斂、隔天補齊」的 **revision 現象**，最新一筆
  之後可能被修正（`:1027` 明講）
- `liquidation` factor **已於 2026-08-02 整個移除**：實測發現本環境對合約 WebSocket
  握手成功但收不到任何 frame，`observed_count=0` 是**假的觀測值**而非真的沒事件。
  改用 REST 看盤口深度（`orderbook_depth`）

### 2.4 幣種專屬 factor 模板（`_coins/`）

`Stage 2 — Feature Extraction/_coins/{BTC,ETH,SOL,BNB,XRP}.yaml` 定義「這個幣要抓哪些
factor」，含幣種專屬項（BNB→`bnb_burn`、XRP→`xrp_supply_burn`、ETH→`gas`、SOL→`tps`、
BTC→`hash_rate`）。BTC 9 個、XRP 7 個。

> ⚠️ **這批目前只是文件，程式還沒讀它**（yaml 檔頭自己註明，2026-08-02 拍板「只寫模板、
> 不動程式」）。實際跑的仍是寫死的 `KNOWN_FACTORS` 八個。`not_applicable` 記的是
> 「資料源／概念上拿不到」（事實），不是「選擇不抓」。

## 3. Stage 3 — Knowledge Layer（純查表，刻意不打 LLM）

**端點**：`GET /api/stage3/{factor_id}`（`:1806`），讀 `Stage 3 — Knowledge Layer/{factor}.md`

**為什麼不打 LLM**：07/13 原文都明講這層是**固定 library、不是推理層**，只回答
「這個 factor 是什麼」。直接讀檔就好，不需要（也不應該）讓 LLM 介入詮釋。
單一事實來源是那份 `.md`，程式只做解析。

內容包含：
- `applicable_days` — **可數值比對的適用區間**（Option B 拍板後新增，讓 Stage 4 的
  `time_horizon_match` 能真的算，不必把散文丟給 LLM 猜）
- `confirms` / `conflicts` / `independent` — 關聯訊號（Stage 6 建圖的**唯一**資料來源）
- `references` — **真實學術／產業出處**，`doi:` / `arxiv:` / `ssrn:` 會被轉成可點擊網址
  （`_ACADEMIC_URL`, `:223`）

**刻意不對齊結論**：funding_rate 的產業文獻偏肯定短期訊號，active_address 近期研究
反而在講預測力減弱，cpi 學界對通膨關係沒有共識，panews 的預測力是狀態依存（極端情緒
下才顯著）——每份都根據各自的資料現實寫，不是同一套模板換名字。

## 4. Stage 4 — Dynamic Evidence Weight Engine（全流程最技術的一層）

```
final_evidence_weight = Prior Weight（算出來）× Context Modifier（LLM 給）
```

### 4.1 Prior Weight：三種來源，換算到同一把尺

**問題**：取絕對值解決了「負號」，沒解決「**單位**」——IC 是相關係數（值域 [-1,1]），
`impact_level` / Domain Knowledge 給的 0.8/0.3 是重要性分數（值域 [0,1]），
兩者放同一個排序鍵比大小，比的**不是同一個被測量的量**。

**共同的尺**：`prior_strength ∈ [0,1]`，定義為「這個 factor 對本次 horizon 的證據強度，
以 |ic| = IC_REF 為強訊號基準」。

| 來源 | 適用 factor | 怎麼來 |
|---|---|---|
| `rolling_spearman_ic` | funding_rate、active_address、momentum | **現場真的算** |
| `rolling_spearman_ic`（離線） | panews_sentiment、etf | 離線算好寫進 `.md`，程式只讀 |
| `impact_level` | cpi（Event） | 讀 `.md` 的分級映射，**不算 IC** |
| `domain_knowledge` | orderbook_depth、price | 讀 `.md`，附為什麼給這個數字的理由 |

#### rolling_spearman_ic 的完整算法（`:425`）

```
IC(horizon) = spearman_corr( factor_value(t), forward_return(t, t+horizon) )
              for t in [now - horizon, now]
```

**兩個關鍵實作細節**：

1. **Spearman 是純 Python 手寫的**（`_spearman_corr`, `:349`）——環境沒裝 scipy/numpy。
   做法是兩序列各自排名（**同值取平均名次**）後算 Pearson，數學上等價於 Spearman。

2. **`now` 錨定在「本地 CSV 實際涵蓋到的最後一天」，不是今天**（`_resolve_ic_anchor_date`,
   `:380`）。這是實測踩出來的坑：本地 CSV 是賽事提供的**靜態**資料集（五幣都停在同一天），
   funding rate 卻是**即時**抓的——直接拿今天當 `now`，`t+horizon` 幾乎必然落在 CSV
   涵蓋範圍外，樣本數會**結構性等於 0**。所以 funding 歷史也跟著抓 anchor 附近的區間
   （`_fetch_funding_history_before` 抓 `[anchor - 2×horizon, anchor]`，多抓一倍是因為
   `t` 必須落在 anchor 前至少 horizon 天，forward_return 才走得完）。

3. **每 8 小時一筆的 funding 依日期分組取平均**（`_daily_funding_series`, `:415`），
   才能跟日頻價格對齊配對。

4. **不設 `min_sample_size` 防呆**（13 拍板）：樣本太少導致的失真 IC 留給後面排序階段
   自然淘汰，這裡如實回報 `sample_size` 讓人自行判斷。

#### IC → prior_strength 的三步換算（`_to_prior_strength`, `:2171`）

```
strength = 1 - exp( -( |ic| × shrink ) / IC_REF )

其中  shrink = √n / (√n + √c)      # 樣本收縮
      IC_REF = 0.1                  # 多少 |ic| 算「強訊號」
      IC_SHRINK_C = 30              # n = 30 時折減剛好 0.5
```

三個設計決定，每個都有明確理由：

- **為什麼用 √n 不用 n**：相關係數的標準誤大致是 `1/√n`，樣本從 100→400 的可信度提升，
  跟 25→100 是同一個量級。用 `n` 會讓大樣本被高估太多。
- **為什麼是連續折減不是門檻**：13 拍板不設防呆。8 筆樣本的 factor **還是有卡片、還是
  進排序**，只是要靠夠強的 IC 才擠得上去，不是被程式先砍掉。係數永遠不到 1.0 也不到 0。
- **為什麼映射用 `1-exp(-x/IC_REF)` 不用 `min(x/IC_REF, 1)`**：後者會讓 |ic|=0.3 跟 0.5
  在收縮後都撞到上限 1.0，**強弱差異被壓平**；指數形式沒有硬上限、單調、天然落在 [0,1)。
- **IC_REF=0.1 的依據**：量化實務中日頻 IC 到 0.05 已算可用、0.1 很強。

> ⚠️ **一個公式解不掉的已知不對稱**（程式碼 `:2230` 明確承認）：回測值會因樣本不足被
> 打折，人工分級的 0.8/0.3 **不會**（分級型沒有「樣本數」這個概念）。這裡**不偷偷補一個
> 折減係數去平衡**——那等於重新引入分組，跟排序拍板打架。做法是把 `basis` 照實帶到卡片上
> 讓人看得到，並記進 13 待處理。

### 4.2 Context Modifier：LLM 讀四條線索給 [0.5, 2.0]

`STAGE4_MODIFIER_SYSTEM_PROMPT`（`:717`）明講「**不要套加權公式逐項計算**，直接綜合
判斷後給一個數字＋理由」——這是 13 拍板的設計：LLM 解釋給出，不是公式加總。

| 線索 | 狀態 | 怎麼算 |
|---|---|---|
| `time_horizon_match` | ✅ **real** | 程式用 `applicable_days` 數值比對（見下） |
| `cross_source_consensus` | ✅ **real**（有同批 factor 時） | 同批 factor 的 trend 方向當場比對 |
| `freshness` | ✅ **real** | 依該 factor 的資料頻率如實描述 |
| `market_regime` | ⚠️ **stub** | 尚未接上真實資料源（FOMC 利率方向） |

**prompt 裡明確要求**：「如果某條線索被標示為『尚未接上真實資料源』，**不要假裝有答案、
不要自己編一個合理的數字**——把那條當作未知，不加分也不扣分，並在理由裡明講哪些是真
數據、哪些是缺資料的中性假設。」

#### time_horizon_match（`_horizon_match`, `:1926`）

```
查詢期間落在 [lo, hi] 內           → score = 1.0
查詢期間 < lo（比適用尺度更短）     → score = horizon_days / lo
查詢期間 > hi（比適用尺度更長）     → score = hi / horizon_days
```
回傳兩種說明文字：`verdict`（一句話，給畫面）與 `detail`（完整算式，給 LLM 參考）。

#### cross_source_consensus（`_cross_source_consensus`, `:2007`）

**只處理 `confirms` / `conflicts`**——`independent` 的定義就是「兩者無關」，本來就沒有
「應該同向」的預期，比方向沒意義，所以**直接跳過、不列為缺口**。

```
confirms 關係：兩者同向  → 與預期一致
conflicts 關係：兩者反向 → 與預期一致（知識庫說會背離，確實背離了）
```

算不出來時要說**為什麼**（關聯 factor 沒卡片／對方結構性沒有 trend），不含糊丟一句
「當未知處理」——那會讓 LLM 分不出是「缺資料」還是「真的沒有關係」，這兩件事對
modifier 的意義完全不同（`_consensus_clue_text`, `:2072`）。

**執行順序上的關鍵設計**（`_stage5_impl`, `:2646`）：Stage 5 是**兩段式**——先把所有
factor 的 Stage 2 跑完，才有「同批其他 factor 今天往哪走」可比。`cross_source_consensus`
必須在 Stage 4 打 LLM **之前**備好，否則它只是事後補的裝飾，進不了 modifier 的判斷。

## 5. Stage 5 — Evidence Card ＋ Prioritization（組裝層）

### 5.1 卡片格式由 `.md` 決定，不是寫死在程式裡

`build_evidence_card()`（`stage_specs.py:462`）——**卡片有哪些格子、fact 有哪些欄位、
哪一格對應到 Knowledge 的哪個欄位，全部讀自 `Stage 5 — .../{factor}.md`**。

以前這些寫死在 `_fact_summary()` 的 if 鏈裡，卡片檔改了程式不會跟著改，兩邊哪天不一致
沒人會發現。現在是讀檔讀出來的，例如：
- `orderbook_depth` 的 fact **沒有** percentile／trend 兩個 key（不是放 null）
- `cpi` 走 Event Knowledge，`primary_horizon` 對應到 `reaction_window`、
  `persistence` 對應到 `expected_duration`（卡片檔用 `→ 欄位名` 記這件事）

### 5.2 排序：單一鍵、取絕對值

```
ranking_value = |evidence_weight|   →  由大到小排序
```

**2026-08-02 拍板兩件事**：

1. **一律照權重排序**，不因 Prior Weight 來源不同（IC 回測值／impact_level 人工分級／
   Domain Knowledge）而分組或另設規則——單一排序鍵就是這層的設計。

2. **比大小時取絕對值**。理由：IC 是相關係數，負值代表**反向訊號**（factor 越高、
   後續報酬越低），那是**有預測力**的訊號不是弱訊號。實測 BTC funding_rate 的
   `ic = -0.55` 是五個 factor 裡強度最高的，照帶號值排會掉到**最後一名**，等於把最強
   的訊號當最弱的。

> ⚠️ **代價**：名次只表達訊號**強度**、不表達**方向**。方向留在卡片的
> `evidence_weight` 正負號與 `weight_direction` 欄位——下游要判多空讀那兩格，
> **不要從名次推**。

**`_weight_direction()`（`:2553`）的一個容易踩的坑**：它讀的是
`prior_weight.raw_value`（**換算前、帶號的 IC 原值**），不是 `final_evidence_weight`
——換算成 prior_strength 之後 final 恆為非負，拿它判方向會永遠得到「同向訊號」。
而且只有 IC 型才有「方向」可言，`impact_level` / Domain Knowledge 給的是重要性分數，
**「方向」這個概念對它不成立**（不是「正向訊號」，是沒有方向可言）。

### 5.3 失敗處理

- 單一 factor 失敗**不會讓整個 Stage 5 掛掉**，但也不靜靜吞掉——如實列在
  `failed_factors` 裡，讓看的人知道這張卡為什麼不在排序結果中
- 算不出權重的卡片**排最後但不刪除**（13 明講「不刪除，只排序」）
- `evidence_coverage` 定義尚未拍板 → **不產生這個欄位**，不假裝有定案

## 6. Stage 6 — Evidence Graph（建圖，不重新判斷關係）

**`_build_evidence_graph()`（`:2758`）的核心主張：這層不推導任何新關係**，只把
Stage 3 Knowledge 已經寫好的 `confirms` / `conflicts` / `independent` 畫成邊。

```
對每張卡片 C：
  對 C.related_evidence.confirms 裡的每個 factor 名 F：
    F 在這批卡片裡 → 畫邊 C --supports--> F
    F 不在         → 記進 referenced_but_no_card（不畫邊、不假造節點）
  conflicts / independent 同理
```

### 6.1 三個回傳部分

| 欄位 | 意義 |
|---|---|
| `nodes` | 這批卡片，`isolated` 標記有沒有連到任何邊 |
| `edges` | **兩端都在這批卡片裡**的關係 |
| `referenced_but_no_card` | Knowledge 提到、但這次沒分析的關聯 factor |

### 6.2 解析細節

- Knowledge 的關係欄位是**自然語言字串**（例：「funding_rate ＋ open_interest（未平倉量）」），
  `_parse_related_factor_names()`（`:2733`）取第一個括號前的識別碼
- 像 conflicts 寫成「（無已知穩定的矛盾對象…）」這種**開頭就是全形括號**的，解析出
  空字串 → **過濾掉**，不當成「有關係但沒卡片」（那句話本來就不在指涉任何 factor）
- `_normalize_factor_token()`（`:2750`）：hyphen 與 underscore 視為同一字元——Stage 3
  有的寫 `hash-rate`、有的寫 `funding_rate`，是撰寫習慣不是兩套命名法，不互通的話
  `active_address` 的 `confirms: hash-rate` 永遠對不上任何卡片

### 6.3 三個誠實揭露的已知缺口

1. **`referenced_but_no_card`**：關係**是真的**（Stage 3 有依據），只是「這次查詢沒把
   那個 factor 也一起分析」。**跟「這個關係不存在」是兩回事**——所以不能略過不提，
   也不能編一個假節點。圖不完整不是資料錯，是這次只分析了這幾個 factor。

2. **cpi 這類 Event Factor 結構性不會主動發出邊**：Event Knowledge 的關係欄位
   （`usually_affects` / `related_events`）跟 Statistical/Sentiment 的三個 key
   **名稱不同**，組裝時讀不到。這裡**不繞過去湊一條邊**——正確做法是回頭讓 Event
   Knowledge schema 也定義對稱的 Graph 用關係欄位，這輪不動。
   ⚠️ 但 cpi **不一定是孤立節點**：別的卡片的 `independent` 可能反過來指向它。

3. **`DEBATE_GRAPH_RULE` 檢查不到孤立節點**：那條規則的前提是「圖裡有邊」，孤立節點
   不會觸發任何規則，等於這道防呆對 Event Factor 沒有保護力（跟缺口 2 同一根因）。

## 7. Adapter — Evidence Card → Evidence 物件

**核心決定：不重寫一套新的推理鏈**（`:2873`）。`agent/reasoning/pipeline.py` 的
`run_reasoning()` 已經是跑得動、900+ 測試覆蓋、release/v1 上線的完整推理鏈。
唯一要做的事是**格式轉換**。

`_cards_to_evidences()`（`:2916`）處理四個 schema 對不上的地方，**老實轉換不假裝完全對應**：

| 問題 | 處理 |
|---|---|
| `Evidence.id` 要求 `ev-\d{3,}`，卡片的 `FUNDING_RATE_BTC` 不符合 | 另外編號，回傳 `id_map` 讓前端把 ev-001 對回可讀名稱 |
| `source_type` 六類 vs Statistical/Event/Sentiment 是**兩套不同分類系統** | `SOURCE_TYPE_BY_FACTOR` 人工對照表 |
| `source_weight` | 讀 `ranking_value`（已換算的 [0,1] 強度），值域定義一致 |
| `related_evidence` | **複用 Stage 6 已解析好的邊**，不重寫一次關係解析 |

**`etf` 沒有完美對應**：映射到 `MACRO`（機構資金流最接近「系統性、非資產微結構」性質），
程式碼 `:2901` **明講這不是精確匹配**，不隱瞞。

### ⚠️ 比較題的兩個關鍵細節

1. **每筆 Evidence 必須帶自己的 `coin`**——推理鏈的 `coins_with_evidence` 就是從
   `Evidence.coin` 推出來的，全部蓋成同一個幣會讓它以為只有一個幣種有證據，
   **比較框架整個失效**。

2. **關係圖必須逐幣各建一張再合併**（`:2926`）——`_build_evidence_graph` 內部用
   `{card["factor"]: card}` 當索引，兩個幣的卡片混在一起時 `funding_rate` 這種同名
   factor 會**互相覆蓋**，畫出 `FUNDING_RATE_SOL --supports--> ACTIVE_ADDRESS_BTC`
   這種根本不存在的跨幣關係。**關係是「同一個幣的證據之間」的關係，不跨幣。**

## 8. Stage 7-9 — 推理鏈、辯論、裁判、信心分數

**端點**：`POST /api/stage789`（`:2976`），內部呼叫 `run_reasoning()`

⚠️ 吃前端**已經拿到的** `evidence_cards`，**不重新呼叫 stage5**——Stage 2/4 的 LLM
判斷每次可能不同，重打一次會讓這裡的證據跟畫面上顯示的**對不起來**，還多等一次昂貴的
pipeline。

### 8.1 四步推理鏈

```
Step A  事實層      1 次 LLM   逐字轉錄證據，不做推論
   ↓                            ＋ grounding 稽核（見 8.2）
Step B  交叉驗證層   1 次 LLM   consistent_signals / contradictions
   ↓                            / structural_context / direction_matrix
Step C1/C2 辯論     最多 4 次   正方 → 反方（看到正方論證後具體批評）
   ↓                            最多 2 輪，反方自報無新論點則提早收斂
Step D  裁判＋結論   1 次 LLM   逐點 verdict ＋ market_judgment
```

**輪次控制**（`pipeline.py:38-58`）：
- `MAX_DEBATE_ROUNDS = 2`——多智能體辯論的增益在第 2 輪後大致飽和
- `has_new_points = false` → `stopped_reason = "converged"`（提早收斂）
- 正式 pipeline 另有 deadline gate（`DEBATE_ROUND_TIME_FACTOR = 2.2`，實測校準），
  **這支 demo 不設 deadline**（不做 15 分鐘賽制的時間預算控制）

### 8.2 Step A 的 grounding 稽核（防幻覺）

**背景**：實測發現 Step A 會在「摘要」的名義下竄改內容——百分位被改寫成年化率、
OI 下降被寫成穩定、甚至幫沒有 RSI 的證據**生出 RSI 描述**。這些錯誤一旦寫進 facts，
**Step C1/C2/D 完全看不到原始證據**（只拿得到 facts + cross_validation），
沒有任何下游機制能發現或修正。

`agent/reasoning/grounding.py` 是**決定性（非 LLM）**的稽核：
- 數字比對（含**是否帶 % 號**——「15.6 百分位」與「15.6%」是不同統計量）
- 指標詞彙比對（含**否定語境判斷**——「未提供 RSI」不算「有 RSI」）
- 方向反轉偵測（來源說下降、fact 寫成穩定 → 攔下）

違規 → 重試一次 → 仍違規則**丟棄該筆 fact**（降級優先，寧可少一筆事實，
不可讓有毒的事實流進 Step B/C）。

### 8.3 Evidence Graph 如何影響辯論

`DEBATE_GRAPH_RULE`（`prompts.py:365`）注入 Step B/C1/C2/D 的 prompt：

> 若證據關係圖顯示多筆證據彼此 **supports**（本質上是同一件事的不同說法），
> **不可把它們當成互相獨立的佐證疊加信心**，只能算一組訊號。
> 若你引用的證據與另一筆 **conflicts**，必須正面處理這個矛盾（說明為何仍採信你引用的
> 那筆），不可略過不提。

### 8.4 裁判逐點判定 → 分數（不是讓 LLM 自報一個整數）

**為什麼改**：實測讓裁判直接吐 -15~+5 的整數**幾乎沒有鑑別力**——同一份輸入重打 5 次
全是 −3；換三種題型、四種幣種全是 −3；把「反方打中兩項」削成「打中一項」還是 −3。
只有把反方整段換成無證據的空話才會翻成 +3。模型輸出的不是「這場辯論值多少分」，
而是「要調一點點」這個念頭——**方向對、幅度沒有解析度**。

**改法**：裁判本來就已經逐點判定攻防（`debate_summary`），改成每點附一個 `verdict`，
**由程式加總**。分數來自可稽核的逐項判定，讀者能自己驗算。

#### 級距隨題型走（第二次修正）

原本只有一套不對稱級距，它預設了「**反方＝質疑者、正方＝被質疑的原判斷**」。
這個前提**只有多源整合題成立**：

| 題型 | 正方 vs 反方 | 前提成立？ |
|---|---|---|
| 多源整合 | 「市場比表面更好」vs「更脆弱」 | ✅ 反方確實在挑毛病 |
| 比較分析 | 「SOL 更值得關注」vs「XRP 更值得」 | ❌ 兩邊都是倡議者 |
| 假設驗證 | 「題目陳述為真」vs「為假」 | ❌ 正方被指派論證一個可能為假的命題 |

**實測後果**：
- **比較題**：同一題只把兩幣語序對調，兩次得到**相同的實質判斷**，但 XRP 站反方時
  扣 7 分、站正方時只扣 3 分——**分數取決於主辦方先寫哪個幣**。
- **假設驗證題**：假設在證據上站不住，系統用最高權重證據給出九次跑裡**最明確的否定**，
  卻拿到**最大扣分 −11**。因為正方被指定去論證一個假命題，必然出現推理瑕疵——那些瑕疵
  是「假設為假」的結果，不是報告品質的訊號。**激勵方向是反的**：假設越明顯為假，
  信心扣得越多。

```python
# 不對稱（multi_source）          # 對稱（comparison / hypothesis_test）
bear_valid:     -3                bear_valid:     -2
bear_partial:   -1                bear_partial:   -1
draw:            0                draw:            0
bull_partial:    1                bull_partial:    1
bull_defended:   1                bull_defended:   2
```

**夾值範圍也必須跟著級距走**（`adjustment_range_for`, `confidence.py:125`）——否則會把
剛拆掉的不對稱從夾值那條路徑放回來：對稱題型下 5 點全給正方是 +10，若沿用全域 +5 上限，
「正方全勝」被砍成 +5 而「反方全勝」的 −10 完整保留，**語序對調的鏡射在夾值後就破了**。

### 8.5 L5 三維信心分數

```
base  = 0.4 × data_confidence + 0.4 × signal_consensus + 0.2 × evidence_strength
final = clamp( base + debate_adjustment )
```

#### ① data_confidence — 資料品質

六類各佔 `100/6`，三檔評分：完整 `1.0` / 部分 `0.6` / 缺 `0.0`。
「部分」給 60% 而非滿分，是為了讓「只有 2 篇新聞」誠實反映出來——**價格資料再漂亮，
來源涵蓋不足就不該說 High Confidence**。

各類的完整門檻（`DATA_COMPLETENESS_THRESHOLD`, `:243`）：

| 類型 | 最少筆數 | 最短窗長（天） |
|---|---|---|
| price | 3 | 14 |
| onchain | 2 | 0 |
| news | 5 | 7 |
| social | 3 | 3 |
| macro | 2 | 14 |
| derivatives | 4 | 7 |

**另外檢查「有效期是否嚴重覆蓋不到主視野」**（R8-2）——修的是實測發現的自相矛盾：
問「過去一年」時，19 筆全 17 天窗的證據仍判六類「完整」拿 100 分，但報告開頭同時
寫著「⚠ 主視野無可用證據」。

**`applicable_categories`（2026-08-02 為 v3 新增）**：這支 demo 的 8 個 factor 只映射到
derivatives/onchain/macro/news/price 五類，**social 從未被使用**。「設計上就不涵蓋」跟
「該補資料但沒補到」是兩件事，不該套同一個扣分公式——傳入子集合時，100 分只在子集合裡
分配，未涵蓋的類別**完全不出現**在 detail 與 why-lines 裡。

#### ② signal_consensus — 訊號一致性

```
Consensus = 100 × ( 1 − 所有來源配對的方向差異平均 / 2 )
```
白話：**隨便抓兩個來源出來，它們意見相同的機率有多高。**

**公式選型（實算 729 種組合後定案）**：
- 原設計的線性 stdev 映射：6 個來源裡 5 個看多只給 25 分（實際上是相當強的共識），
  且 **35.7% 的情境擠在 0-20 分區間**、失去鑑別度
- 候選的 `100×|mean|`：更差（**53.9% 擠在低分區**），且「全部中性」給 0 分——
  但那其實是完美一致、只是沒方向
- 兩兩一致度：三個問題都沒有，分佈開展在整個區間（**0-20 佔 0%**），語意也最好解釋

**只納入當前訊號**——結構脈絡（長於主視野的帶）不參與投票，否則假矛盾會從這條路徑復活。
表態來源不足 2 個時降級為中性 50 並標記（一個來源談不上「共識」）。

#### ③ evidence_strength — 證據強度

各類平均 `source_weight` × 類別覆蓋度折減。**刻意不引入 LLM 主觀評分**——需求方的核心
訴求是可解釋、可複現，若讓 LLM 給「Price=90, Social=60」，等於在剛拆掉的主觀基底旁邊
裝一個新的。

#### 不進入扣分路徑的東西

`structural_context` **不進入任何扣分路徑**——跨尺度差異是**位置關係不是矛盾**，
那正是這套設計要修的核心問題。

## 9. Execution Log（命題交付項目）

命題文件把 `execution_log.jsonl` 列為交付項目。這支 demo API 是**無狀態的**、一個 stage
一個 HTTP 端點，沒有「一次執行」的檔案可寫，所以改成**每個請求各自收集、隨回應回傳**，
前端跨三段（Stage 1／Stage 2-5／Stage 6-8）累積成一條時間軸，可下載成同格式 `.jsonl`。

- 用 **contextvars** 而非逐層傳 logger——Stage 5 會 `asyncio.gather` 併發跑 8 個 factor
  的 Stage 2/3/4，逐層傳要改十幾個函式簽名；contextvar 在 asyncio 下每個 task 自帶副本
- `_capture_log()` **支援巢狀**：stage6 內部直接呼叫 stage5 實作，兩層紀錄合併成
  **同一條時間軸**，不會分裂成兩份
- 欄位對齊正式 pipeline 的 `agent/schemas.LogEntry`（`ts`/`phase`/`action`/`detail`/
  `status`/`layer`/`metrics`），兩邊可並排比對
- **`elapsed_ms` 是最有價值的欄位**——命題有 15 分鐘硬上限，「哪一層吃掉多少秒」是
  事後檢討與現場要不要降級的依據

**實測數據**（真實 Bedrock）：Stage 2-5 約 30 秒／25 筆紀錄；Stage 6-8 約 164 秒
（辯論 2 輪自然收斂）。⚠️ 累計工作時間會**大於**牆鐘時間，因為 factor 是併發跑的。
